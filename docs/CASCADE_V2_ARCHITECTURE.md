# Архитектура 3X-UI KIT Cascade 2.0 (draft)

> Это новая архитектура **установки с чистого сервера**, не патч существующей установки KIT. Пока в репозитории находятся спецификация и генератор конфигурации, а не готовый production installer.

## Роли

- **EXIT**: минимальный Xray-core, VLESS + REALITY inbound только для предыдущего узла, один `freedom` outbound в интернет; отдельной панели 3X-UI нет.
- **RELAY (0..N)**: минимальный Xray-core, собственный VLESS + REALITY inbound и VLESS + REALITY outbound к следующему узлу. Никаких `freedom` outbound и прямого клиентского egress. RELAY не имеет панели и пользователей.
- **ENTRY**: оригинальный функционал 3X-UI KIT (панель, пользователи, подписки, выбранные клиентские протоколы, nginx, TLS и маскировка). Все **клиентские** подключения направляются в VLESS outbound к следующему узлу.

Схема: клиенты (IPv4) -> ENTRY -> (IPv6/VLESS+REALITY) -> RELAY[n] -> ... -> RELAY[1] -> EXIT -> интернет.

## Строго обратный порядок

1. На EXIT выбрать роль EXIT. Определить публичный IPv6 (несколько адресов — спросить какой), выбрать SNI и порт, установить Xray, создать собственный UUID и X25519 REALITY ключи, запустить Xray, проверить и вывести `vless://UUID@[IPv6]:PORT?security=reality&type=tcp&...`. Адрес **обязательно в квадратных скобках**.
2. На RELAY выбрать роль RELAY, вставить ссылку **следующего** узла (выходного либо уже установленного RELAY), проверить формат и работу транспорта. Создать inbound с новым UUID/ключами, outbound из введённой ссылки и вернуть собственную новую VLESS-ссылку. Повторять любое число раз.
3. На ENTRY выбрать ENTRY, вставить ссылку ближайшего узла. Установить 3X-UI KIT, выбрать клиентские протоколы, их порты, TLS/REALITY/SNI и способ маскировки. Настроить outbound, сохранить критические правила локального API и сделать outbound маршрутом по умолчанию для клиентских inbounds.
4. Финальная проверка по цепочке: клиентский IP на внешнем сайте совпадает с EXIT; выпадение любого RELAY не приводит к прямому выходу с ENTRY/RELAY.

**Ссылка — чувствительные учётные данные** (UUID + параметры подключения). Не писать её в публичные логи или репозиторий; мастер получает её интерактивно или из закрытого файла.

## Переиспользование оригинального KIT

На ENTRY оставить всю существующую логику создания и обслуживания протоколов KIT; заменить только оркестрацию первоначальной установки, нужные проверки доступности, выбор исходящих маршрутов и диагностику. Проверки доступности Telegram и SNI выполняются по корректному маршруту, а не обязательно через прямой IPv4 с ENTRY. Маскировка **клиентских** протоколов не должна зависеть от SNI межсерверного REALITY. После установки оставить команды `kit user`, `kit net`, `kit backup`, `kit check`.

## Изоляция и управление

- Для клиентского трафика ENTRY и RELAY — fail-closed: отсутствует fallback на `freedom`.
- Системный трафик `apt`, `curl`, DNS и SSH НЕ становится проксированным автоматически: VLESS — proxy, не интерфейс VPN. Управление системными соединениями и запрет прямых исходящих требуют отдельной проверенной политики (с учётом SSH-ответов IPv4, IPv6 RA, DHCPv6, UFW, аварийного отката).
- В момент первой установки чистые серверы должны иметь доступ к репозиториям пакетов и бинарнику Xray; затем политика исходящих подключений выбирается отдельно. Нельзя включать жёсткий firewall до проверки связности.
- На RELAY можно ограничить входящий порт VLESS известным IPv6 предыдущего узла, если адрес известен. На EXIT аналогично.
- Сервисные каналы управления и ответы SSH не должны попадать в цепочку и не должны блокироваться.
- При падении любого hop клиентский egress прекращается; у серверов остаётся гарантированный административный доступ.
- На релизе: резервное копирование, хэширование/подпись релизов, версионирование, безопасный откат, мониторинг hop health.

## Технические оговорки

- VLESS/REALITY/Vision по TCP между хопами может переносить UDP-запросы прокси, но UDP-over-TCP может ухудшать задержку для Hysteria2, TUIC и AmneziaWG. Проверить UDP, MTProto, TCP, DNS и MTU на тестовых узлах.
- Для полного сохранения клиентского IP на EXIT понадобятся дополнительные механизмы; обычный Xray `freedom` создаёт новые исходящие соединения с адреса EXIT.
- Каждый RELAY поднимает **свой** inbound REALITY: вставленная ссылка описывает *следующий hop*, а новая возвращаемая ссылка — *текущий hop*.
- Не объединять старый прототип `cascade-dev` в новый master. Его design был рассчитан на доработку уже установленного KIT.
- Типовые Xray-поля и формат REALITY проверить с фиксированной версией Xray-core до применения на VPS.

## План релизов

1. **v2.0-alpha1**: библиотека ссылок, генерация EXIT/RELAY/ENTRY-outbound, офлайн тесты; нет системных изменений.
2. **alpha2**: установщик Xray systemd для EXIT и RELAY, установка из GitHub, проверки порта и IPv6.
3. **alpha3**: чистая установка ENTRY поверх штатного KIT с выбором всех протоколов и отдельной маскировкой.
4. **alpha4**: интеграционные проверки MTProto/AmneziaWG/TUIC/Hysteria2, безопасная маршрутизация и kill switch, диагностика.
5. **beta**: 2/3/4-хоповые испытания, обновления, восстановление, release workflow.
