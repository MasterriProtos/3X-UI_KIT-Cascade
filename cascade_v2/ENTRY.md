# KIT-Cascade v2: установка ENTRY на чистую Ubuntu 24.04

> **Alpha / draft PR #2**. Действующий российский KIT и настроенный EXIT не изменяются. ENTRY устанавливается **только на новый чистый сервер**, который принимает клиентский IPv4. Автоматического системного kill switch **нет**.

## Архитектура

```text
Клиенты TCP/UDP по IPv4
         ↓
 ENTRY / 3X-UI KIT v3.9.0 / Xray-core v26.6.27
         ↓ VLESS + REALITY + Vision / IPv6
 EXIT / Xray-core v26.11.9
         ↓
      Интернет
```

Для запуска **EXIT уже должен быть установлен и проверен**. Нужна только сохранённая VLESS-ссылка от EXIT. Она содержит учётные данные: её не следует публиковать в issue, чате или репозитории.

## Установка

На новом ENTRY VPS под root:

```bash
sudo apt-get update
sudo apt-get install -y git python3 ca-certificates
git clone --branch multi-hop-v2 https://github.com/MasterriProtos/3X-UI_KIT-Cascade.git
cd 3X-UI_KIT-Cascade
python3 -m unittest discover -s cascade_v2/tests -v
sudo python3 cascade_v2/install.py install --role entry
```

Если клонировали раньше: `cd 3X-UI_KIT-Cascade && git pull --ff-only`.

1. **Вставьте** приватную VLESS-ссылку от EXIT в запрос `ENTRY` (ввод скрыт). Если её формат неверен или введено `y`/`n` вместо ссылки, мастер объяснит ошибку и предложит повторить ввод; `q` отменяет операцию. Требуется полная строка, начинающаяся с `vless://`, а не HTTP-ссылка, IP или UUID.
2. Программа проверит формат (глобальный IPv6, порт, UUID, REALITY/Vision, ключи) и TCP-доступность EXIT.
3. На вопрос «Установить 3X-UI KIT на ENTRY?» ответьте **`y`** (да) или **`n`** (нет). Enter означает «нет».
4. Запустится оригинальный мастер установки KIT: выберите **стандартный или индивидуальный набор протоколов** (в том числе REALITY, XHTTP, Hysteria2, TUIC, AmneziaWG, MTProto, WireGuard), затем **сайт маскировки REALITY, собственный домен или автоматический подбор** (свой REALITY SNI можно задать даже без публичного сертификата панели), а в каскадном режиме отдельно можно указать SNI для **XHTTP** и FakeTLS-сайт для **MTProto**. REALITY и запасной REALITY-2 используют основной SNI; WS/Trojan/VMess используют TLS-сертификат сервера. Далее выбирается тип сертификата и панель.
5. Сразу после установки совместимой версии Xray, но **до создания клиентских inbounds**, в шаблон панели добавляется VLESS outbound `to-next-hop` через ваш EXIT и обязательный TCP/UDP-маршрут.
6. Сервис 3X-UI тестирует outbound **реальным HTTP-запросом через Xray**. При провале запуск клиентских протоколов отменяется.
7. Затем KIT продолжит штатную установку подписок, nginx, пользователей и выбранных протоколов. MTProto в Cascade использует Xray SOCKS bridge вместо прямого TCP из процесса mtg; внутренний порт SOCKS5 выбирается автоматически среди свободных.
8. При полном успехе `/etc/kit-cascade/entry/state.json` принимает статус `installed`.

Встроенные сценарии KIT могут иногда предупреждать, что исходящий IP не равен IP ENTRY: это нормально для каскада. Проверяйте итоговый IP **из клиента**, а не командой `curl` непосредственно на Linux ENTRY.

## Продолжение после ошибки API на этапе ядра Xray

Если установка остановилась с сообщением **«Неожиданный ответ API: xraySetting отсутствует»** после шага \`[3/6] Ядро Xray\`, это известная ошибка версии alpha: ответ \`POST /panel/api/xray/\` в 3X-UI v3.9.0 возвращает JSON-**строку** с объектом \`xraySetting\`. С версии фикса она правильно разбирается.

**Не удаляйте установленную панель/сертификаты и не запускайте заново \`install --role entry\`.** Исправленный установщик поддерживает отдельный контролируемый повтор:

\`\`\`bash
cd /root/3X-UI_KIT-Cascade
git pull --ff-only
python3 -m unittest discover -s cascade_v2/tests -v
python3 cascade_v2/install.py resume-entry
\`\`\`

Для \`resume-entry\` обязательны: уже установленная панель 3X-UI и её локальные данные API, сохранённая root-only ссылка EXIT, **0 записей пользовательских inbounds**, отсутствие завершённого KIT, отдельного Xray-сервиса и любых признаков частичного применения CASCADE. Предварительная проверка не меняет конфигурацию; при неожиданных файлах и существующих клиентах продолжение блокируется.

После ответа \`y\` штатный мастер KIT снова спросит выбор протоколов, сайт маскировки и IP, но **переиспользует текущие панель, ядро и VLESS-ссылку EXIT**. Перед созданием клиентских подключений он применит исправленный cascadе outbound и проверит его реальным запросом. Если процедура откажется продолжать, ничего вручную не удаляйте: сначала разберите вывод проверок.

## Проверки после установки

```bash
cd /root/3X-UI_KIT-Cascade
sudo python3 cascade_v2/install.py entry-status
sudo systemctl is-active x-ui
sudo kit check
```

Подключитесь с клиента к выбранному протоколу ENTRY и откройте `https://api.ipify.org`. Должен отобразиться публичный IP EXIT. Затем **временно** проверьте, что если EXIT отключится, клиент не получит прямого выхода через ENTRY; сервер EXIT должен оставаться доступным для SSH.

## MTProto и Telegram без SNI — отдельный TCP/8445

В современных Telegram FakeTLS ClientHello может не содержать ожидаемое SNI или его не удаётся разобрать `nginx ssl_preread`. При этом `kit check --deep` успешно проверяет искусственное рукопожатие. Если **реальный Telegram через SSH-туннель в локальный nginx → mtg работает, а через публичный 443 — нет**, проблема локализуется в общем TLS/SNI-мультиплексоре nginx. Безопаснее дать MTProto свой TCP/8445, не изменяя REALITY/XHTTP и не отключая FakeTLS.

Для **уже установленного ENTRY**:

```bash
cd /root/3X-UI_KIT-Cascade
git pull --ff-only
bash scripts/mtproto-public-cascade.sh
ss -lnt '( sport = :8445 )'
```

Скрипт работает только на установленном Cascade ENTRY, проверяет порт 8445 и существующую конфигурацию, сохраняет резервную копию `/etc/nginx/kit-stream.conf.pre-mtproto-8445`, добавляет отдельный nginx `stream server` с `proxy_protocol on` → `127.0.0.1:10445`, проверяет `nginx -t`, перезагружает только nginx и откатывает конфигурацию при сбое. **Не меняет** UFW/облачный firewall, Xray, mtg, SQLite или EXIT. Внимание: если при диагностике ранее был создан временный `127.0.0.1:24445`, он пока сохраняется; не восстанавливайте старый полный nginx-конфиг поверх новой рабочей настройки.

Обязательно проверьте внешний доступ к `ENTRY:8445/tcp`. При включённом firewall **разрешите только TCP/8445**, отдельно в UFW и в панели VPS-провайдера, где необходимо. `443/udp` и `443/tcp` других протоколов не менять. После этого в Telegram меняется **только адрес порта на `8445`**, старый `secret` остаётся прежним; SSL, сертификат и uTLS fingerprints к этому не относятся.

Если нужно, чтобы и `kit user link пользователь --telegram`, и ссылки 3X-UI теперь выдавали TCP/8445, установите обновлённый KIT с сохранением старой версии:

```bash
bash -n scripts/kit.sh
cp -a /usr/local/bin/kit /usr/local/bin/kit.pre-cascade-mtproto-8445
install -m 755 scripts/kit.sh /usr/local/bin/kit
kit __mtproto
kit check --deep
```

Это осознанно заменяет только оболочку KIT той же версии `1.2.1` и добавляет host-группу для `8445` через штатный API; пользовательские секреты не меняет. Старые ссылки на `443` могут остаться в Telegram, замените их новыми. Для **новых установок Cascade** скрипт `3x-ui.sh` сразу добавляет TCP/8445 в nginx и генерирует актуальные ссылки. У обычных (не Cascade) установок схема не изменяется.

## Диагностика MTProto через EXIT

Если `kit check --deep` показывает запущенный `mtg` и успешный FakeTLS, но предупреждает **«с сервера не видно серверов Telegram»**, это предупреждение о **прямом** TCP-соединении с ENTRY, **не о цепочке через EXIT**. Для MTProto с `routeThroughXray:true` требуется проверять локальный SOCKS5-мост `mtg → Xray → to-next-hop → EXIT → Telegram`.

```bash
cd /root/3X-UI_KIT-Cascade
git pull --ff-only
python3 cascade_v2/install.py entry-mtproto-probe
```

Проверка только читает SQLite 3X-UI и Xray template, **не выводит MTProto-секреты и не меняет сервер**. Она сверяет `routeThroughXray`, `outboundTag`, `routeXrayPort` и делает SOCKS5 CONNECT через реальный локальный порт к нескольким адресам Telegram на TCP/443. Успешное подключение подтверждает работоспособность маршрута на уровне TCP, **но не гарантирует полную авторизацию Telegram, подлинность ссылки и работу всех DC**. Ошибка `Connection refused` на локальном SOCKS — повод проверить генерацию Xray-конфига; SOCKS5-код ошибки при обращении к Telegram — повод изучить исходящие подключения EXIT. В конце по необходимости проверьте логи `journalctl -u x-ui -n 80 --no-pager` и `tail -n 80 /var/log/x-ui/3xui.log`, удалив перед отправкой токены, пароли и секреты.

В будущих установках `kit check` не будет выводить ложное предупреждение о прямой недоступности Telegram для Cascade ENTRY. На ранее установленном KIT обновление только Git-репозитория **не заменяет** `/usr/local/bin/kit`, но команда `entry-mtproto-probe` доступна напрямую из обновлённого checkout.

## Ложный failed при проверке TCP-outbound в панели 3X-UI

В закреплённой панели **3X-UI v3.9.0** тест TCP для outbound с IPv6 может показывать:
\`dial tcp: address 2a04:...:443: too many colons in address\`.

Это **ошибка тестировщика панели**, а не проверка исправности VLESS/REALITY. В исходном коде 3X-UI \`extractOutboundEndpoints\` склеивает \`host + ":" + port\` через \`fmt.Sprintf("%s:%d", host, p)\`, тогда как \`net.Dial\` требует \`net.JoinHostPort(host, strconv.Itoa(p))\` (скобки для IPv6). **Не добавляйте скобки в поле \`settings.vnext[].address\` конфигурации Xray**: там должен оставаться чистый IPv6 без порта.

После полной установки ENTRY проверьте **реальный HTTP-запрос через Xray** (не TCP-кнопку панели):

\`\`\`bash
cd /root/3X-UI_KIT-Cascade
python3 cascade_v2/install.py entry-status
python3 cascade_v2/install.py entry-probe
\`\`\`

Команда \`entry-probe\` проверит правило принудительной маршрутизации и запустит штатный \`testOutbound\` 3X-UI в режиме \`real\` — с фактическим HTTP-запросом через локальный временный Xray. Эта команда **не изменяет настройки**. Если установка ещё частичная и состояния ENTRY нет, сначала разберитесь с \`resume-entry\`. Окончательный IP выхода дополнительно проверьте из клиента, подключённого к ENTRY.

## Что НЕ меняется автоматически

- **SSH и правила UFW/nftables**: оригинальному KIT передаётся `--no-ufw` из-за отсутствия подтверждённой аварийной консоли. Если UFW/облачный firewall активен, входящие TCP/UDP порты клиентских протоколов требуется открыть вручную **после проверки**.
- **System-wide proxy**: `apt`, `curl`, systemd и другие хостовые процессы могут обращаться к интернету с IP ENTRY. Клиентский трафик, обработанный Xray, маршрутизируется через EXIT. Полную блокировку хостового прямого egress будем добавлять отдельно с аварийным откатом.
- **Upstream KIT update**: в alpha автообновление выключено и `kit update` блокируется, чтобы случайно не переписать каскадный routing.

### Ответы на вопросы

Подтверждения удаления временной ссылки, установки панели, использования самоподписанного сертификата, выбора запасной маскировки и отката: **y / yes / да = да**, **n / no / нет = нет**, **Enter = нет**. Установщик также понимает визуально похожую кириллическую `у` вместо латинской `y` и невидимые символы, случайно вставленные из буфера обмена. Если ответ не распознаётся, будут показаны Unicode-коды введённых символов (без секретов). Пункты меню с несколькими вариантами выбираются **номерами**, а поле VLESS требует **полную ссылку**, а не y/n. Секретный ввод не показывает вставляемые символы.

## Повтор после конфликта SNI до установки панели

Если первый запуск завершился с сообщением `Для XHTTP нужен отдельный SNI` **до шага `Пакеты`**, на диске может остаться только закрытая ссылка EXIT `/etc/kit-cascade/entry/next-hop.txt`. Это не требует переустановки сервера. Обновите ветку и повторите запуск:

```bash
cd /root/3X-UI_KIT-Cascade
git pull --ff-only
python3 -m unittest discover -s cascade_v2/tests -v
sudo python3 cascade_v2/install.py install --role entry
```

Установщик разрешает новую попытку **только при отсутствии 3X-UI, Xray и признаков частично выполненной полноценной установки**. Он спросит «Удалить сохранённую ссылку и начать заново?» с ответом **`y` / `n`** (Enter = нет), после чего удалит прежнюю приватную VLESS-ссылку `/etc/kit-cascade/entry/next-hop.txt` и пустую папку ENTRY. Старая ссылка не используется: **новую VLESS-ссылку EXIT нужно вставить повторно**, а ответы на вопросы о протоколах, SNI и маскировке будут заданы с начала. Если в папке есть другие файлы (например, резервные копии), автоматическое удаление будет запрещено.

Конфликтующий SNI теперь вызывает повторный запрос, а не завершение процесса. Введите другой домен либо нажмите Enter для сохранения предложенного, если он не конфликтует с REALITY/MTProto. **Никакой очистки других данных сервера, установленной панели, SSH или файлов EXIT не производится**.

Если на VPS уже есть `/usr/local/x-ui`, `/etc/x-ui/x-ui.db` или Xray, **не удаляйте их и не пытайтесь обойти защиту** — сначала соберите диагностику. Секретную ссылку и содержимое `install-result.env` не присылайте в публичные каналы.

## Ошибка или частичная установка

Если установка не завершилась, **не выполняйте обычный оригинальный установщик поверх результата**: он может создать клиентские подключения без каскадного маршрута.

```bash
sudo python3 cascade_v2/entry.py status
sudo journalctl -u x-ui -n 80 --no-pager
```

Сохранение исходного Xray-шаблона: `/etc/kit-cascade/entry/xray-template-before.json`. Закрытый файл next-hop: `/etc/kit-cascade/entry/next-hop.txt`. Оба доступны только root. Скрипт не публикует ссылку в логах.

Для **ручного fail-closed восстановления**:

```bash
sudo python3 cascade_v2/install.py entry-restore
```

Требуется ответ `y` (да) или `n` (нет; Enter = нет). Команда **останавливает x-ui и отключает её автозапуск ДО возврата старого шаблона**. Затем через sqlite3 восстанавливает Xray-конфигурацию в остановленной SQLite базе. Сервис **не запускается автоматически** (иначе уже созданные клиентские inbounds могли бы выйти в интернет напрямую).

Создаётся резервная копия базы `/etc/kit-cascade/entry/x-ui-before-restore.db`. Для возобновления службы требуется отдельное осознанное действие администратора после проверки конфигурации и клиентов.

## Пока не проверено на реальном ENTRY

- Комплексная работа всех выбранных протоколов с разными клиентами, особенно UDP (Hysteria2, TUIC, AmneziaWG).
- Публичная доступность подписок и автопродление сертификатов у разных провайдеров.
- Реальный MTProto через путь mtg → Xray SOCKS → EXIT.
- Защита от прямого исходящего трафика **всех системных процессов**.

В CI проверены Python-тесты, синтаксис bash, актуальный Xray JSON и реальный VLESS+REALITY-транспорт между разными версиями ядра. **CI не заменяет испытание на тестовом ENTRY VPS**.

См. также [документацию архитектуры](../docs/CASCADE_V2_ARCHITECTURE.md) и [установку EXIT/RELAY](README.md).
